# OwnTV 应用瘦身方案（体积 + 无用功能）

> 范围：`OwnTV_Core`（分支 `mobile`，HEAD `c4d9d0cb`）的 `:core` / `:player-core`，以及宿主 `OwnTV_Mobile`（分支 `mobile-mini`）的构建与分发侧。
> 基线日期：2026-11-07。所有体积数字为**本机实测**，测量命令见 §6；标注"估算"的项未经 before/after 构建验证。
> 前置文档：`OwnTV_Mobile/extras/SLIMMING_PLAN.md`（App 层剔除，已实施）、`OwnTV_Mobile/docs/设置页改造方案.md`（设置项取舍判据）、`OwnTV/docs/i18n-apk-size-baseline.md`（语言过滤测量法）。
> 本文不重复 App 层已完成的剔除，只处理**它故意留下的 core 残留**与**它无法触及的体积分项**。

## 0. 结论摘要

### 0.1 一句话结论

**代码与资源侧的瘦身收益已经见底，剩余 83.2% 的 APK 是预构建 FFmpeg/libmpv 动态库。** 继续删 Kotlin 功能对体积的贡献是百 KB 量级；真正的体积杠杆只有三个：ABI 分发、FFmpeg 编译裁剪、去掉 bundled SQLite。

## 1. 前提与边界

### 1.1 三个已核实的前提

1. **vendored core 与当前分支逐字节一致。** `OwnTV_Mobile/vendor/OwnTV_Core` 由 `22858554` 从 `c4d9d0cb` squash 而来；`diff -rq` 对比 `core/` 目录（含双方未提交改动）为空。所以本文对 core 的分析同时适用于 mobile-mini 正在编译的那份源码。
2. **core 已可从源码编译。** `6d0c2c65` 用 `includeBuild` 替换 maven 坐标，`owntvCore = "1.0.70"` 只是占位数字。这是本轮能真正删 core 的前提——上一轮 `SLIMMING_PLAN.md` 的硬约束 D1「不碰 core」已解除。
3. **core 是 library 模块，本身不做任何裁剪。** `:core` / `:player-core` 全仓 **0 命中** `abiFilters`、`splits`、`localeFilters`、`isMinifyEnabled`、`shrinkResources`、`productFlavors`、`buildTypes`。所有 dex/资源/ABI/语言裁剪都由宿主 app 决定。core 侧能做的只有「少编译源码、少放资源、少声明依赖」。
   - 好消息：R8 通道是干净的。`core/consumer-rules.pro` 5 行全是注释、零规则；`player-core/consumer-rules.pro:7-13` 只有 2 条 JNI 必需的精准 keep。没有宽包名 keep 阻碍裁剪。

### 1.2 删 core 的影响面（关键约束）

**TV App 消费同一份 core。** `OwnTV/app/build.gradle.kts:348` + `OwnTV/gradle/libs.versions.toml:82,86` 指向 pinned 产物 `tv.own.owntv:core:1.0.69`。

- 改 core `mobile` 分支源码**不会立刻打断 TV 编译**，只在 TV 升 core 版本时爆发。
- TV 当前在 `QwnTV-mini` 分支，也在做精简：`e51d482b` 已删天气、`c53612ce` 已转中文单语、`9a05e570` 已删品牌 accent 开关。**但 TV 仍全量使用体育**（`app/src/main/java/tv/own/owntv/features/sports/` 下屏幕文件仍在）。
- 因此：**两端都已弃用的功能可以直接删；只有一端弃用的必须做成可选装配，不能直删。**

### 1.3 沿用 mobile-mini 的三条纪律

来自 `OwnTV_Mobile/docs/设置页改造方案.md:206-214` 与 `SLIMMING_PLAN.md` §0.2，本文全部继承：

1. **整行移除 + 内部固定默认**，而不是置灰只读（占空间、搜索仍命中、易被误判为故障）或保留但锁定（"等于不能选的选项，与减负目标相反"）。
2. **不删数据、不改 schema、不改备份格式。** 旧值留在库里只是不再参与逻辑；降级回旧版仍能读回。
3. **默认值由宿主注入，不写进 core。** 共享库不应为单一宿主改默认值（`设置页改造方案.md:302-311`）。本文 A2/B4 涉及 core 改动时，一律做成**可选装配**而非改默认。

## 3. 瘦身项

### A1 · 单 ABI / per-ABI 分发 —— 最大且最便宜的一刀

**现状**：`OwnTV_Mobile/app/build.gradle.kts:73-83` 的 `standard` flavor 同时打包 `arm64-v8a` + `armeabi-v7a`；全仓 **无 `splits`、无 `bundle` 配置**。CI（`.github/workflows/android.yml:220-263`）产出 one universal APK + 一个 x86_64 模拟器包，经 GitHub Release 侧载分发。

**实测**：arm64-v8a = 23,802,136 B，armeabi-v7a = 21,948,872 B。**每个用户都下载了自己永远不会执行的那 21.9 MB。**

**两个方案**：

| 方案 | 做法 | 结果 | 代价 |
|---|---|---|---|
| **A1-a（推荐）** | `standard` 只保留 `arm64-v8a` | 54,985,187 → **33,036,315 B（−39.9%）** | 放弃 32 位 ARM 设备 |
| A1-b | 加 `splits.abi { enable = true; include("arm64-v8a","armeabi-v7a") }`，CI 发两个包 | 各约 33 MB / 31 MB | 侧载用户需自行选包；Release 页面变复杂 |

**推荐 A1-a**。理由：分发渠道是 GitHub Release 侧载而非 Play Store，**AAB 用不上**，per-ABI APK 会把选包负担丢给用户；而 2026 年的 32 位 ARM Android 设备已极少。若必须保留 32 位支持，退 A1-b。

**注意**：这是宿主 app 的改动，core 侧无需配合（core 无 abiFilters，全量透传）。`x86_64` flavor 保持不变，模拟器不受影响。

### A2 · bundled SQLite → framework driver

**现状**：`core/build.gradle.kts:208` 引入 `androidx.sqlite:sqlite-bundled:2.6.2`，`core/di/DatabaseModule.kt:35` 用 `BundledSQLiteDriver()`。理由写在 `core/build.gradle.kts:205-207`：minSdk 26 意味着 Android 8 只有 SQLite 3.18，缺 UPSERT / 窗口函数。

**实测**：`libsqliteJni.so` arm64 = 1,310,776 B，v7a = 1,253,332 B（AAR 还带 x86/x86_64，被 app 的 abiFilters 挡掉）。**A1 之后仍剩 1,310,776 B。**

**已备好的退路**：`sqlite-framework` 已经是依赖（`core/build.gradle.kts:211`），`DatabaseModule.kt:33-34` 的注释明确写着「改这一行即可，代码库其他地方不知道差别」。**切换本身是一行。**

**但有两个真实阻塞，必须先解决**：

| 阻塞 | 证据 | 需要的 SQL 版本 | 解法 |
|---|---|---|---|
| 4 个 DAO 用窗口函数 | `database/dao/ChannelDao.kt`、`CustomCategoryDao.kt`、`MovieDao.kt`、`SeriesDao.kt` | 3.25 → **API 30+** | minSdk 26 → 30 |
| `MIGRATION_45_46` 用 `ALTER TABLE … DROP COLUMN` | `database/OwnTVDatabase.kt:1317` | 3.35 → API 33+ | **改写成建表-拷贝-换名**，否则 minSdk 30 仍不够 |

已核实的**不构成阻塞**项：UPSERT 需 3.24（API 30 的 3.28 满足）；搜索用的是 **FTS4**（`content/SearchReader.kt:284`，framework 早已支持）；全仓无 `RETURNING`、无 `STRICT` 表、无 `json_extract`/`json_each`、无其他 `DROP COLUMN`。

**实施**：
1. 把 `OwnTVDatabase.kt:1315-1319` 的 `MIGRATION_45_46` 改成标准 12 步表重建（该列注释 `:1311-1313` 已说明「每行都是 NULL，nothing is lost」，所以重建无数据风险）。
2. `DatabaseModule.kt:35` → `AndroidSQLiteDriver()`；移除 `core/build.gradle.kts:208`。
3. minSdk 26 → 30（`core/build.gradle.kts:26`、`player-core/build.gradle.kts:22`、宿主 `app/build.gradle.kts:34`）。
4. 同步改 `core/build.gradle.kts:205-207` 与 `DatabaseModule.kt:28-31` 的理由注释。

**代价与决策点**：放弃 Android 8/8.1/9/10（API 26–29）。**这是需要你拍板的取舍**，不是纯技术项。若不愿放弃，A2 整项跳过——注意「运行时按 API 选 driver」不能省体积，因为 `.so` 仍会打包。

**core 是共享库**：minSdk 与 driver 改动会连带影响 TV。建议做成 gradle property 分支（照抄 §4.1 的 `owntv.libmpvLocalRepo` 范式），让 TV 继续 bundled、mobile 走 framework；或两端同步抬 minSdk。**不要单方面改 core 默认值**（§1.3 纪律 3）。

### B1 · 删除 `core/weather` —— 唯一的真孤儿

**这是全仓唯一两端皆零引用的功能包。**

| 核查项 | 结果 |
|---|---|
| TV App 引用 | **0**（`app/src/main/java` 无命中；仅命中过期构建产物 `generated/baselineProfiles/startup-prof.txt`，非源码） |
| Mobile App 引用 | **0** |
| TV mini 分支 | 已主动删除：`e51d482b mini: remove the weather chip, its Settings page and clock colours` |
| Room entity / DAO | **无** |
| Manifest 组件 | **无** |
| core 内部耦合 | 仅 `di/DataModule.kt:30,154` 两行注册 |
| 规模 | 2 文件 / **126 行** / 5,779 B |

**实施**：删 `core/src/main/java/tv/own/owntv/core/weather/` + `DataModule.kt:30,154`；清 `settings/SettingsRepository.kt:3183-3184,3259` 的 4 个键（`WEATHER_LOCATION`/`CLOCK_WEATHER_COLOR`/`WEATHER_ENABLED`/`WEATHER_FAHRENHEIT`）、`ClockColors.weather`、`BackupKeys` 三处、以及 `values/strings_settings.xml:223,2943` 与 `values/strings.xml:299` 的文案键（含各语言副本）。

**备份安全性**：weather 走 `exportSettings()`/`importSettings()` 的键白名单。从 `BackupKeys` 移除后，旧 `.own` 里的多余键被 `importSettings` 忽略，**不会恢复失败**。

**收益**：APK 层面 KB 级，可忽略。**做它的理由是消除死代码与死配置，不是体积。** 零风险，建议顺手做掉。

### B2 · 品牌图标锁定单一变体

**现状**：`core/brand/AppIcon.kt:26-36` 定义 **10 个变体**（Petrol/Sunflower/Cobalt/Tomato/Board/Eggshell/Olive/OliveCream/Pixel），每个变体在宿主 Manifest 里有一个 `activity-alias` 固定引用其 mipmap（`OwnTV_Mobile/app/src/main/AndroidManifest.xml:101,118,135,152,169,186,203,…`）。

**为什么 shrinkResources 救不了**：全部变体都由 Manifest alias 可达，资源裁剪器无法证明任何一个不可达，**10 套全量打包**。全仓无 `getIdentifier` 动态查找，也无 `tools:keep`/`tools:discard` 规则。

**实测**（`core/src/main/res/` 下 `drawable*` + `mipmap*` = 150 文件 / 909,226 B）：

| 变体 | 文件 | 字节 |
|---|---:|---:|
| pixel | 16 | 234,044 |
| eggshell（`AppIcon.DEFAULT`） | 16 | 88,236 |
| olive_cream | 16 | 87,829 |
| sunflower | 16 | 83,563 |
| olive | 16 | 82,341 |
| cobalt | 16 | 83,136 |
| tomato | 16 | 82,686 |
| petrol | 16 | 81,157 |
| board | 16 | 78,329 |
| 共享 | 6 | 7,905 |

**锁定 eggshell 可删 8 个变体 = 813,085 B 原始资源**；锁定 pixel 则省 667,277 B。PNG 已压缩、XML 可压缩，**APK 实收估算 0.6~0.8 MB**（约占 `res/` 分项的 30%）。

**判据一致性**：TV mini 已经做过同类取舍——`9a05e570 Settings: fold ambient glow into Glass & background; drop the brand accent switch`。「换图标」正是典型的配置复杂、收益不大。

**实施**：宿主 Manifest 删 8 个 alias（保留默认那个）；core 侧 `AppIcon` 枚举收敛为单值或保留枚举但删其余变体的资源引用；连带删 `app_icon_*` 字符串键。`brand/AppRestartActivity`（`core/src/main/AndroidManifest.xml:88`）在锁定后也无用，可一并摘除。

**注意**：`AppIcon` 是枚举，而宿主 `proguard-rules.pro:24` 有 `-keep enum tv.own.owntv.**`（Enum.name 往返 DataStore/备份）。删枚举值前要确认旧持久化的图标名能归一化到保留值，照抄 `AppLocales.normalize()` 的做法。

### B3 · core 语言目录 27 → 3（注意：APK 收益为 0）

**必须澄清的一个常见误判**：core 有 26 个 `values-*` 翻译目录、`strings*.xml` 共 **161 文件 / 94,170 行 / 10,072,999 B**，但**宿主 `localeFilters` 已经把它们挡在 APK 之外**（`OwnTV_Mobile/app/build.gradle.kts:146`）。实测 release 的 `resources.arsc` 只含 `()`/`(zh-rCN)`/`(zh-rTW)`，633,008 B。

**所以删 core 语言目录对 APK 体积的收益是 0 B。** 真实收益在别处：

| 收益项 | 量级 |
|---|---|
| 已发布 `core` AAR 缩小 | res Deflate 从 2,633,351 B 降到约 0.7 MB |
| 仓库/检出体积 | −9.45 MB（26 个翻译目录合计 9,451,250 B） |
| i18n CI 与生成器耗时 | 显著下降 |
| 翻译维护面 | 45 条 catalogue → 3 条 |

### C1 · FFmpeg 编译裁剪 —— 天花板最高，但在上游仓

**这是唯一能把 APK 压到 30 MB 以下的路径。**

`libavcodec.so` 单 ABI 就 **10,433,376 B**（arm64），占整个 APK 的 19.0%；FFmpeg 六个库双 ABI 合计 29,914,388 B（54.4%）。A1 之后单 ABI FFmpeg 仍有 15,439,912 B。

**为什么这么大**：libmpv 以预构建 AAR 引入（`tv.own.owntv:libmpv:2026.11.0`，`gradle/libs.versions.toml:48,136`，`player-core/build.gradle.kts:106-110` 用 `api` 暴露）。AAR 实测 32,179,902 B，含 3 个 ABI × 10 个 `.so`。这是**全功能 FFmpeg 构建**，带齐了所有编解码器、滤镜、协议。

**裁剪方向**（需改 `OwnTV_libmpv` 的 buildscript，**该仓未在本机检出**）：
- `--disable-encoders` / `--enable-encoder=…`：IPTV 播放器只解码，不编码。编码器可几乎全删。
- `--disable-decoders` + 白名单：只保留 H.264/HEVC/VP9/AV1/MPEG-2/AAC/AC3/EAC3/MP3/Opus/FLAC 等实际会遇到的格式。
- `--disable-filters` / `--disable-muxers` / `--disable-demuxers` 白名单。
- `--disable-programs`、`--disable-doc`、`--disable-debug`、`--enable-small`。

**收益未量化**——必须实际构建对比才知道，**不要相信任何未经测量的百分比承诺**。

**风险高**：IPTV 源的格式长尾极长，删错一个解码器就是某批频道直接失播，且失败现象是「某个用户的某个源播不了」，回归成本远高于普通改动。必须配套真实源矩阵测试。

**已有基础**：`player-core` 自己手写了 4 个 `.java`（`ffmpeg/FfmpegAudioDecoder.java` 等）替代 `media3-decoder-ffmpeg`，说明团队已有 FFmpeg JNI 层的裁剪经验。`-Powntv.libmpvLocalRepo`（`settings.gradle.kts:23-29`）已支持指向本地构建的 libmpv，**验证通道现成**。

**建议**：单独立项，先做 A1/A2/B2 拿到确定的 44%，再评估 C1 是否值得。

### C2 · core 体育残留 —— 被 TV 阻塞，且比预想更棘手

`SLIMMING_PLAN.md:446-455`（D8）明确接受残留：`core.sports.*` 全部类、体育文案、`HomeRow.LIVE_SPORTS`、`StageGlyph.SPORTS` 全留，验收口径是「APK 里仍有 core 的体育类不算失败」。

**一个好消息**：**体育没有 Room 表**。状态走 `filesDir/sports` JSON（`di/DataModule.kt:202`），配置走 DataStore（`settings/SettingsRepository.kt:813-828`）。`@Database`（`OwnTVDatabase.kt:68-126`，version **53**）里无 sports entity/DAO。**所以删体育不需要 migration**——这比原以为的风险低得多。

**但有三个阻塞**：

1. **TV 仍全量使用体育**（`OwnTV/app/src/main/java/tv/own/owntv/features/sports/` 屏幕文件仍在，`OwnTVApp.kt:159`、`features/shell/OwnTVShell.kt:1391`）。TV 升 core 版本时会编译失败。
2. **Mobile 自己还编译期依赖 core.sports**：`OwnTVMobileApp.kt:186-187` 调 `MatchAlertScheduler.rearmAll()` + `stopService(LiveMatchCardService)` 做**升级清理**——取消老版本留下的比赛闹钟。删了这个垫片，从带体育版本升级的用户会残留闹钟。**至少要保留一个发版周期。**
3. **耦合面比看起来宽**，删包必须同改：`nav/MainSection.kt:20`（`SPORTS(R.string.sports_title)`）、`player/PlayerControls.kt:87,90`、`model/HomeRow.LIVE_SPORTS`、`ui/StageGlyph.kt:76`、`sync/work/KoinWorkerFactory.kt:89`、`di/DataModule.kt:155-204`、`settings/SettingsImportRules.kt:4-6,45-66`（直接 import `SportsCatalog`/`SportsConfig`/`SportsRefreshPolicy`）、`backup/BackupManager.kt:190`（写）与 `:1193`（读）、Manifest 三组件（`core/src/main/AndroidManifest.xml:159,166,180`）。

**备份的正确删法**：读侧是 `root.optJSONObject("sportsConfigs")?.let { … }`（`BackupManager.kt:1193`），**缺失即跳过**。所以删写侧（`:190`）不会让旧备份恢复失败；但若连 `SportsConfig`/`SettingsImportRules` 一起删，`:1193` 会编译失败。**正确做法是删写侧、把读侧降级为 no-op，而不是整块删类。**

**收益诚实评估**：4,490 行 dex + 3 语言的 261 个体育键，**估算 150–300 KB**，占 APK 不到 0.6%。**投入 3–4 人日换 0.6%，性价比远低于 A1/A2/B2。**

**建议**：等 TV mini 也删掉体育后再做，届时两端一致，可直删而不需可选装配。当前只做一件低成本的事：把 `DataModule.kt:155-204` 抽成独立 `sportsModule`，为将来解耦铺路（§4.1）。

## 4. 实施路线

### 4.1 先铺一个开关范式（后续项的前提）

core 全仓**没有任何功能开关 / flavor / 可选模块机制**，43 个功能包无条件编译，DI 只有 3 个文件且 `di/DataModule.kt:34-404` 是单体巨模块。两端都整包加载（TV `OwnTVApp.kt:132`、MOB `OwnTVMobileApp.kt:161-162`）。

建议按同样形状引入 `-Powntv.features=`（或 `owntv.slim=`），做两件事：
1. **DI 拆分**：把 `DataModule` 里的 weather(:154)、sports(:155-204)、launcher(:316-322) 抽成独立 module，宿主按需 `modules(...)`。
2. **依赖可选**：`tvprovider`、`sqlite-bundled` 按 property 决定是否声明。

## 5. 风险与回归口径

### 5.1 必须守住的底线

1. **不改 Room schema**（阶段 4 改写 migration 语句属例外，但版本号与表结构不变，且必须导出 schema JSON）。当前 version 53，无 destructive fallback。
2. **不改备份容器与密封格式**（`.own` = ZIP + `backup.json`，密封 `OWNTVBK1`，`backup/BackupManager.kt:110` version 26）。只改「写哪些块」，读侧保持 `optJSONObject?.let` 容错。
3. **旧持久化值必须能归一化**：图标名、语言标签、被删设置项的旧值都要有明确回落，照抄 `AppLocales.normalize()` 与 `SlimPlayerDefaults` 的幂等写入范式。
4. **删枚举值前检查 keep 规则**：宿主 `proguard-rules.pro:24` keep 了 `enum tv.own.owntv.**`（Enum.name 往返 DataStore/备份）。

### 5.2 每项的验收断言

| 项 | 验收 |
|---|---|
| A1 | `unzip -l` 只含 `lib/arm64-v8a/`；arm64 真机安装 + 直播/影视/回看各播通一条；x86_64 模拟器包不受影响 |

| B2 | `aapt2 dump resources` 只含保留变体；旧持久化图标名归一化后不崩；应用图标正常显示 |
| B3 | `gen_supported_locales.py check` 通过（非 STALE）；`aapt2 dump configurations` 仍只有 3 语言；`core/lint.xml` 注释已更新 |

### 5.3 已知盲区

- **JVM 单测测不出 Android 平台差异**：`unitTests.isReturnDefaultValues = true`，Android 的 `org.json` 在 JVM 单测返回默认值，**读备份 JSON 的逻辑不能直接单测**，要把纯策略拆出来（`BackupProfiles.decide()` 就是这么做的）。A2 的 migration 与 B1 的备份兼容必须真机验证。
- **core 无未使用字符串检测工具**：`tools/i18n/validate_strings.py` 检的是反向问题（译文有、源无），`check_hardcoded_strings.py` 是 Kotlin 字面量 ratchet。**删功能后 CI 不会报孤儿键**，需手工清或另写检测。
- **本文所有 dex/字符串收益均为估算**，未经 before/after 构建。只有 §0.2 与各项 `.so`/资源字节是实测。

## 6. 测量方法（可复现）

```bash
APK=app/build/outputs/apk/standard/release/app-standard-release-unsigned.apk

stat -c %s "$APK"                                    # 总字节
unzip -l "$APK" | grep "lib/"                      # 每个 .so 的 stored 字节
unzip -l "$APK" | grep resources.arsc              # 资源表
unzip -v "$APK"                                    # 压缩后 vs 原始，用于算占比

# 分项汇总（本文 §0.2 的来源）
unzip -l "$APK" | grep "lib/" | awk '{n=$4; sub(/.*\//,"",n);
  if(n ~ /^lib(av|sw)/) f+=$1; else if(n=="libmpv.so") m+=$1;
  else if(n=="libsqliteJni.so") s+=$1; else if(n=="libc++_shared.so") c+=$1;
  else o+=$1} END {printf "FFmpeg=%d mpv=%d sqlite=%d libc++=%d other=%d\n",f,m,s,c,o}'

# 实际打包的语言（需 ANDROID_HOME）
"$ANDROID_HOME"/build-tools/*/aapt2 dump configurations "$APK"
python3 tools/i18n/check_pseudo_locales.py --apk "$APK" --mode release
```
